October 2026 upgrade

A marathon coach that runs the numbers before it answers

The July version of this coach retrieved passages from 14 knowledge cards and answered with [n] citations. It could quote "about a minute per °F" but could not tell a 3:30 runner what 75°F costs, or what a 1:42 half means for the finish. The October version can call tools: a finish-time and wall-risk model fitted on Boston splits, a heat model fitted on Boston results against race-day weather, and a pace table. I froze 43 test questions before running anything, then put the same questions to three systems: the model on its own, the July RAG coach, and the tool coach.

The comparison

Three systems, one frozen question set

Of the 43 questions, 26 ask for numbers (42 scored values in all) and 17 are strategy questions, including the seven from July. Each numeric question stores the tool calls that answer it, and src/gold.py computes the expected value and its tolerance from the models' own output, so nothing is typed by hand. A finish time counts as correct within a quarter of the model's 80% interval (at least a minute); a heat slowdown within a quarter of its range (at least 30 seconds); a wall-risk percentage within 5 points; a pace within 2 seconds. The set was committed at eb413bf before any system saw it, and the eval refuses to run if the file's hash changes. Every system got the same question text and the same model, claude-sonnet-5-5, through the Claude CLI.

Faithfulness, relevance and context precision come from an LLM judge (the same model). The bare answer is judged against the passages the RAG coach retrieved for that question, as in July. Citation validity and the unsourced-number check are computed in code.

The tool coach got all 42 values. That figure is closer to circular than it looks: the expected values come from the same models the coach calls, so the numeric score measures whether a system reproduces the models, and a perfect score means the loop picked the right tool, passed the right arguments and copied the result back on all 26 questions. It did, with no JSON repairs and no step-cap stops. Whether the models themselves are right is a separate question, covered under the limitations.

Without tools, the RAG coach got 21 of 42 and the bare model 14. Retrieval settles the card-arithmetic questions (RAG 8 of 8, bare 3 of 8) and does little for the rest. On heat the RAG coach applied the July card's minute-per-degree rule, which for a 3:30 runner at 75°F gives about 25 minutes against the model's 16.9. On finish times both baselines landed inside the tolerance half the time, since doubling the half split is a fair guess, but they missed every wall-risk figure: the bare model guessed between 25% and 65% where the model said 0% to 19%.

The number check separates the systems more clearly than the judge does. In 28 of 43 RAG answers at least one number had no source, mostly the model's own arithmetic ("a 1:42 half is about 4:50/km", "about 204 minutes"). The tool coach did this 3 times: once it turned 17.7% into "a 1-in-6 chance", and twice it gave "30 km" advice without citing the card that says so. On faithfulness the two coaches are close (0.90 against 0.88). One coach answer failed outright: asked "how much slower will race-day heat around 80°F make me?", it asked for the runner's finish time instead of answering. The judge scored that answer 0.30 for relevance and 1.00 for faithfulness, because an answer with no claims has nothing unsupported in it.

The tool coach made 2.3 model calls per answer and needed no more time than RAG (median 7.2 s against 7.4 s; means 8.0 s and 11.8 s). Each of its calls carried a short prompt and returned a short reply, a JSON action, where the single RAG call carries five passages and writes the whole answer. Latencies are wall-clock with four answers running at once.

How the loop works

Plan, call, read, repeat

The Claude CLI takes text in and gives text out, with no function-calling interface, so src/agent.py runs the loop itself.

  1. Ask for one action. The model sees the question, the tool list and every earlier step, and must reply with one JSON object: a tool call or a final answer.
  2. Run the tool. predict_finish and heat_effect are the models from the pacing and heat projects, vendored with their source commits. pace_table does even or fade splits, with fade sizes read from the negative-split card. retrieve_cards searches the cards. A calculator covers sums so the model does not do arithmetic in its head.
  3. Feed the result back. Passages are numbered [1], [2] and tool results [T1], [T2], so the answer can cite both.
  4. Repair or stop. A reply that is not valid JSON gets one retry with the parse error quoted back. After six tool calls the model must answer with what it has.
  5. Check the numbers. A deterministic post-check pulls every number out of the answer and looks for it in the question, the tool results and the passages the answer cites, allowing for rounding and for clock times written as minutes or seconds. Anything unmatched is flagged.

The model results carry their own caveats, copied from the holdout checks in the source projects, and the coach is told to pass them on. The pace model has no weather input, and on its 2024 holdout its 80% interval at 35 km covered 74% of runners. The heat model did not beat a flat no-weather guess on its 2015–2019 holdout (2.26% error against 2.15%), and it ignores dew point, which did not beat dry-bulb temperature in cross-validation.

Retrieval

Hybrid search and reranking, measured: no gain on 14 cards

The July page guessed that BM25 plus a cross-encoder would help, as it did for the wine sommelier RAG. On the frozen questions, scored by which cards each question needs, it did not. Dense search already finds a relevant card in its top three for nearly every question, and no mode's mean reciprocal rank differs from dense by more than its bootstrap noise. The coach keeps dense search, which is also the fastest of the embedding-based modes.

The knowledge base

Fourteen cards, six from my own studies

The corpus ships in the repo as markdown, one card per topic, each with a > Source: line. Eight cover established training principles: carbohydrate fueling, carb-loading, tapering, hydration and sodium, even pacing, the long run, race week, and hills. Six are distilled from analyses I ran and published:

Negative splits
2.5% of 31,912 Boston 2014 finishers ran a negative split; about 94% slowed, median +14%.
The wall
Pace inflects at about 30 km; 27% of finishers slowed by more than 25% late in the race.
Heat
About one minute slower per °F of race-day heat at Boston (the July card; the heat tool is the newer model).
Courses
Boston +101 s and New York +78 s against Berlin, from a simulated field with planted penalties. The card labels them as simulated; they are not measurements of the courses.
Super-shoes
About 67 seconds of the modern elite gain is footwear.
BQ standards
Across 22 age and sex brackets there is no average gender gap, but women's brackets vary three to four times more in difficulty.

Limitations

What the numbers don't show

The numeric score is only as good as the models behind it. The heat model did not beat a flat no-weather guess on its own 2015–2019 holdout, and the pace model's late-race intervals ran narrow on 2024. A system that matches them perfectly is consistent, and that does not make it correct. In the recorded runs the coach passed both caveats on.

The judge is the same model as the three systems. The bare model's faithfulness is judged against the passages the RAG coach retrieved, so a correct claim the cards don't contain counts against it. That figure fell from 0.76 in July to 0.33 here: the judge prompt now scores one answer at a time and counts numbers as claims, so the two runs are not comparable.

I wrote all 43 questions, and the numeric ones hand the system every input it needs. Real runners leave things out, which is how the one failed answer happened. Each system answered each question once, so run-to-run variation is not measured.

The number check is rule-based. Its rounding allowance (2.5% of the source value) lets through some arithmetic done in the model's head: in one recorded run the coach gave an adjusted-finish range of "205 to 219 minutes" that no tool computed, and the check passed it. It also flags correct paraphrases such as "1 in 6". I changed its rules twice after the run began, to count the tool descriptions and digits in result field names (the "95" in lo95_min) as sources, and to skip bold list numbers. Every answer was rescored with the final rules; under the first version it fired on 11 coach answers and 29 RAG answers.

The retrieval comparison uses 43 questions and relevance labels I wrote. The course card's figures are simulated, and the card says so next to each one.

The first evaluation: grounded against bare

In July the coach was scored on seven strategy questions: faithfulness 0.98 grounded against 0.76 bare, answer relevance 0.95, context precision 0.78, citation validity 1.00. Those seven questions are s01 to s07 in the new set.

2026-10-28: superseded by the three-system run above, which uses a different judge prompt (one answer at a time, judged against that system's own context) and a pinned model, so the two sets of scores are not directly comparable.
